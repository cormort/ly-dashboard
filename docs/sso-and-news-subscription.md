## 0. 先看清楚這個 app 現在的樣子（決定成本的事實）

| 項目 | 現況 | 影響 |
| --- | --- | --- |
| 執行形狀 | 單一 node 行程（`server/index.mjs`）＋ SQLite（`data/ly.db`）＋ Vite 靜態前端（`web/dist`） | 沒有多實例、沒有外部 session store；接 SSO 時身分層要自己加 |
| 對外綁定 | 預設 `127.0.0.1`（`LY_HOST`，見 `server/config.mjs`） | 目前只有本機看得到；要給機關用必須改綁內網位址並處理 TLS |
| 唯一的保護 | `POST /api/v1/sync`：有 `LY_SYNC_TOKEN` → 要求 `x-sync-token`；沒設 → 只有 loopback 能用，`LY_HOST` 非 loopback 時**直接 403 停用**（`authorizeSync()`，`server/index.mjs`） | 唯讀 API 完全開放；「誰能看」這件事目前不存在 |
| 帳號／角色／稽核 | **完全沒有** | `change_log`、`sync_runs` 是「資料異動」與「同步紀錄」，不是使用者行為稽核 |
| 新聞來源 | 媒體 RSS（中央社／自由／聯合／公視）每小時由 GitHub Action 收進 `news-data` 分支（`.github/workflows/collect-news.yml`），同步時匯入 `articles`；委員新聞走 Google 新聞 RSS。**2026-10-07 起**：本機的伺服器也可以把抓到的新聞推回同一個分支（`LY_NEWS_PUSH=1`，見 `server/news-push.mjs`／D228）—— 兩台裝置互相看得到對方抓的 | 「持續收集、不重打來源」的機制已經有了（見 D113–D117、D138–D139） |

### 新聞的資料模型（跟下一節的成本直接相關）

`topic_news(topic, url, title, source, published_at, fetched_at, title_key)`，目前的 topic 有四種：

- `dgbas`：主計總處／地方主計處兩組查詢（`server/ingest.mjs` 的 `DGBAS_QUERIES`）。
- `entities`：**基金／機關／行政法人**新聞。名稱每批 N 個合成一次 OR 查詢（`entityNewsTerms()` 從 `fund-config.json` 取簡稱），
  標題提到具名單位才收（`mentionsKnownEntity()`），有時間預算與接續游標（`news_entity_cursor`）。
- `official:<姓名>`：**33 位部會首長**（`server/officials.json`）逐人查詢，`ingest.mjs` 尾端那圈就是它。
- `news`／`news_entity` 之類的類別由 `queries.mjs` 的 `kindOfTopic()` 推導，前端「新聞」頁與「機關／首長」頁都吃同一份。

**也就是說：機關與首長新聞的抓取已經在跑了**，缺的不是「抓」，是「讓使用者挑自己要的、並能推播」。

## 1. 之後要接機關的 Single Sign-On

### 1.1 先確定是哪一種（工程量差一個數量級）

| 類型 | 典型場景 | 需要跟資訊單位拿什麼 | 相對成本 |
| --- | --- | --- | --- |
| AD／LDAP | 機關內網、桌機網域登入 | LDAP 位址、bind 帳號、群組 DN | 中（要處理連線與群組對應，密碼驗證自己來） |
| OIDC | Entra ID、Google Workspace、Keycloak、政府雲身分服務 | issuer、client id／secret、redirect URI 白名單、claims | **低（建議）** |
| SAML 2.0 | 較舊的機關 SSO | metadata XML、IdP 憑證、SP 憑證、attribute 對應 | 高（要自己驗 assertion 與簽章、處理時鐘偏移） |
| 政府共同規範（TW FidO 等） | 跨機關自然人憑證／行動自然人憑證 | 申請流程、API 文件、測試環境 | 中高（流程長，技術上多為 OIDC 變體） |

**第一步永遠是同一件事**：問資訊單位「我們的系統要用哪一套、請給 dev/staging 的 metadata 與測試帳號」。沒拿到之前不要動工。

### 1.2 兩條實作路線

**路線 A：前面的反向代理終結 SSO（推薦）**

    瀏覽器 →（nginx／Caddy／機關既有 WAF 或 API Gateway）→ 本機 node

代理層做 OIDC／SAML，通過後把身分放進 header（例 `X-Auth-Request-Email`、`X-Auth-Request-Groups`），
app 只信任「來自代理的請求」並且**只聽內網或 loopback**。

- 這個 repo 幾乎不用改：把 `LY_HOST` 改成內網位址、把 `authorizeSync()` 從「loopback-only」改成「來自代理 ＋ 具備 admin 群組」即可。
- 憑證輪替、登出、session 逾時、MFA 政策全部留在代理層；換 IdP 時 app 不動。
- 缺點：多一層要維運；「只信任代理」這件事要真的做到（只綁內網、或驗一個共享 header 密鑰）。

**路線 B：app 內做 OIDC client**

- `openid-client` ＋ cookie session（例如 `iron-session`），加一張角色表（`user → 角色`）。
- 要自己處理：state/nonce、redirect URI、token 更新、session 撤銷、CSRF。
- 好處是不用維運代理；代價是身分邏輯進了 app，之後改 IdP 要動程式。
- 若最後是 SAML，這一條會再貴一級（簽章驗證、assertion 重放防護、憑證到期）。

### 1.3 具體要動的地方（以路線 A 為例）

1. `server/config.mjs`：`LY_HOST` 由 `127.0.0.1` 改成內網位址；新增「信任代理」開關（例如 `LY_TRUST_PROXY_HEADERS=1` ＋ `LY_PROXY_SECRET`）。
2. `server/index.mjs` 的 `authorizeSync()`：改成「token **或** 已登入的 admin 角色」；唯讀 API 維持公開或改成需登入（這是一個產品決定，見 §1.5）。
3. 前端（`web/src`）：顯示目前登入者；未登入時的降級（公開頁照看、同步鈕隱藏）。
4. 稽核：`sync_runs` 加一個 `actor` 欄（誰按的同步）；若要「誰看過什麼」再另談（通常不需要，且會增加個資風險）。
5. 部署：內網主機、TLS 憑證、SQLite 備份（目前是單檔 + WAL，排程複製即可）、launchd 服務化（`scripts/launchd/` 已有樣板）。
6. 把 `/api/v1/sync`、`/api/v1/sync-sources`、`/api/v1/sync-runs`（如果含內部資訊）列進「需授權」清單。

### 1.4 成本

- 路線 A：**0.5–1 天**（含登入狀態顯示與測試）。
- 路線 B（OIDC）：**1–2 天**；SAML 再加 1–2 天。
- 真正的成本不在寫程式，而在機關端流程：要 metadata、要測試帳號、要跑資安審查／弱點掃描，
  有時要原始碼檢測報告。**那些通常比工程本身久**，要先問清楚需要哪些文件。

### 1.5 建議順序

1. **先把「需要登入才能用的功能」壓到最小**：目前只有「觸發同步」一件事。其他都是唯讀的公開資料。
2. 先做「只綁內網 ＋ 反向代理 ＋ 信任 header」的最小版 —— 就算先不接 SSO，之後換上去也不用改 app。
3. 再接 SSO（OIDC 優先、SAML 最後）。
4. 這條路的副產品是：把網站從「某台機器上的 localhost」變成「內網的一個服務」，本來就是對的方向。

## 2. 增加「訂閱機關或首長的新聞」的成本

### 2.1 已經有的（可以直接用，不必重做）

- Google 新聞 RSS 的查詢產生器：`newsFeedUrl(name, q)`、`entityFeedUrl(terms)`（`server/ingest.mjs`）。
- 委員新聞：每位在職委員一組查詢，只收標題含姓名（D19 的規則）。
- **機關首長**：`server/officials.json` 的 33 位（院長／副院長／各部會部長…），逐人查詢，存成 `topic_news` 的 `official:<姓名>`。
- **基金／機關／行政法人**：`entityNewsTerms()` ＋ 批次 OR 查詢 ＋ 時間預算 ＋ 接續游標（`entities`）。
- **主計總處**：`dgbas` 兩組查詢（中央／地方主計處）。
- 媒體 RSS 每小時收集（不重打新聞網站）；每 host 400ms 節流；`LY_NEWS_*` 一整組可調參數。
- 通知機制：`scripts/notify-telegram.sh`＋每日排程（粉專那條已在用）。

### 2.2 「訂閱」還缺什麼（按層次估）

| 層次 | 內容 | 成本 | 備註 |
| --- | --- | --- | --- |
| a. 只加關鍵字 | 把要看的機關／首長／基金加進名單（config） | **0.5 天** | 部會首長與基金機關**已經有了**；要補的多半是地方政府、國營事業、特定機關 |
| b. 「我的訂閱」 | 使用者可挑選、只看自己關心的、記住選擇 | **1–2 天** | 「記住選擇」要先決定身分：有登入就存後端，沒有就存網址參數／本機 |
| c. 每日推播摘要 | 每天早上把訂閱的新聞推到 Telegram／email | **＋0.5–1 天** | 通知管線已有；主要成本是「摘要格式」與去重 |
| d. 抓機關官網自己的公告 | 不靠 Google 新聞，直接抓機關網站的公告列表 | **每個網站 0.5–2 小時**，且要長期維護 | 政府網站常常沒有 RSS；改版就會壞，這是最貴的一項 |

### 2.3 結論

**不高。** 純資料面幾乎不用做（抓取、分類、去重、節流、可觀測性都在），
真正的增量是「使用者介面 ＋ 記住偏好 ＋ 推播」，約 **1.5–3 天**。若只要關鍵字清單（層次 a），**半天**。

### 2.4 風險

- **Google 新聞的雜訊**：機關名會有同名公司、轉載、業配。現有做法是「標題要提到具名單位」才收（`mentionsKnownEntity()`），
  但「主計處」「教育部」這類詞仍偏寬，要像委員那樣用人名／全銜收斂。
- **同名首長**：`officials.json` 已經有 hint（兩個字的名字要再含關鍵字），沿用即可。
- **自己抓 HTML 的來源會腐壞**：每多一個「官網解析器」就多一份長期維護成本，優先選有官方 RSS 的機關。
- **授權**：目前只存標題＋連結＋來源、不轉載內文（Google 新聞的 description 也不存摘要），要維持這個邊界。

### 2.5 建議

1. 先做層次 a：把名單補到你真的想每天掃的機關（先 10–20 個），跑一週看雜訊。
2. 雜訊可接受再做層次 b／c；**如果要做 b，就得先有登入（§1）**，否則只能存在瀏覽器或網址上。
3. 官方 RSS 優先於 Google 新聞：準確度高、雜訊低，代價是每個來源一支解析器。

## 3. 附帶：粉專貼文的互動數（讚／留言數）

這一輪已經把**管線**做好並驗證（整理表兩個新欄位、Apps Script 重部署、後端／DB／API／前端、兩層測試全過），
但抓取端**目前一律留空**：粉專頁把置頂／精選貼文排在前面、互動列常常只渲染一則、
而日期來自頁面內嵌 JSON 的最新時間、摘要取自 DOM 第一篇 —— 三者不一定是同一則，
證明不了「是同一則」時依 fail-closed 原則留空（實測 5 位 → 0 位可證明）。

要填數字有兩條路（成本差很多，尚未選）：**(A)** 逐篇開貼文永久連結頁，在那一頁同時拿日期與互動數
（可驗證、覆蓋率高；每位多開一頁，每天約多 20 分鐘、對 Facebook 的請求量約多一倍；要先解「怎麼從粉專頁找到那一則的永久連結」）；
**(B)** 直接用「這頁渲染出互動列的那一則」配「內嵌 JSON 的最新時間」（零額外成本，但沒有機械證據擔保，有標錯篇的風險）。
細節與決策紀錄見 `DECISIONS.md` D207–D215。**使用者已決定先不實作。**
