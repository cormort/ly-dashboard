# 「立委觀測站」(legislator-intelligence-dashboard) 可行性評估

評估日期：2026-09-30 · 受評版本：上傳的 zip（7 檔、16 KB 原始碼）
評估方式：**實際跑起來 + 實打立法院 API + 真實瀏覽器驗證**，不是純讀碼推測。

---

## 一句話結論

**技術上完全可行，資料源是真實、公開、免金鑰的；但「現況這包」在瀏覽器裡拿不到任何真實資料**，
只會顯示 2 筆示範假資料（甲黨/乙黨），長期停在「同步失敗」。
要把 demo 變成能上線的東西，需要 **4 個具體修正 + 1 個代理層**，估 **1–2 人日**（含驗證）。
可行性高、現況可用性低。

| 項目 | 評價 |

| 資料源可用性 | ✅ 實測 HTTP 200，無需金鑰、無需登入 |

| 修復後成果 | ✅ 實測 113 位委員、11 個委員會、64 位召委、真實黨籍選區 |

## 二、必修的四個問題（依嚴重度）

### B1. CORS：這是「能不能用」的生死線（阻斷級）

`data.ly.gov.tw` 不回應 CORS 標頭，瀏覽器一律拒絕讓前端 JS 讀取。
App 的重試機制只是把同一個必然失敗的請求做 3 次，最後落回 `demo` 陣列 ——
**使用者看到的是兩個不存在的立委（林怡安/陳宏宇，標示「示範資料」）**，
若直接上線展示，這是實質的錯誤資訊風險。

README 第 16 行已誠實註明「若瀏覽器因 CORS 阻擋…請改由後端代理」，方向正確，但程式沒做。

**修法**：加同源代理（Vite `server.proxy` + `preview.proxy`；上線用 Cloudflare Worker / Vercel function / 小 Node 服務）。
我在 PoC 裡只加了 5 行 config。

### B2. Node 代理的 SSL 陷阱（實作時一定會撞到）

第一次加完代理，兩個端點都回 **502**：

```
Error: write EPROTO ... SSL routines:final_renegotiate:unsafe legacy renegotiation disabled
```

立法院主機要求 unsafe legacy renegotiation，而 Node/OpenSSL 預設拒絕（curl 不會，所以「curl 測得過、程式打不通」很容易誤判成程式錯）。

**修法**（已驗證有效）：代理層用
`new https.Agent({ secureOptions: crypto.constants.SSL_OP_LEGACY_SERVER_CONNECT, keepAlive: true })`。
**這點必須寫進文件**，否則接手的人會卡很久。

### B3. 委員會欄位解析錯誤（資料顯示直接壞掉）

ID9 的 `committee` 實際長這樣：

```
"第11屆第1會期：內政委員會;第11屆第2會期：內政委員會;第11屆第3會期：內政委員會;..."
```

程式用 `split(/[、,，;；\n]/)` 切開後**沒有剝掉「第N屆第M會期：」前綴**，於是：

- 委員會下拉選單與圖表出現 **70 種分類**（正解是 18 種／當屆 11 種）；
- 每張委員卡片的「委員會」欄變成一長串「第11屆第1會期：內政委員會、第11屆第2會期：內政委員會…」；
- 篩選、圖表統計全部失真。

實測：修掉前綴後，下拉清單回到乾淨的 11 個委員會（內政、外交及國防、經濟、財政…）。

### B4. ID14 是「第 4–11 屆全歷史」資料集，被當成當屆名單用

- ID14 回傳 11,702 筆、涵蓋第 4 到第 11 屆；傳 `term=11&sessionPeriod=5` **無效**（照樣回 11,702 筆），**只能在客端過濾**。
- 程式只用「姓名」join 兩份資料，且 `convener` 是「任一屆次曾任召委就 true」：
  - **122 / 123** 位現任委員的委員會清單被歷史屆次污染（平均每人 10.1 個委員會標籤）；
  - 召委統計 **84 人**，正解是當屆 **64 人**（ID14 term 11 去重後 68，再扣掉已離職者）；
  - 同名不同人（69 個名字跨屆重複）會被合併成同一人。

**修法**：以 ID9 的 `term` 為準，只保留 ID14 同屆資料（PoC 已做，結果即 113 人／64 召委）。
更好的做法是逐會期（`sessionPeriod`）呈現「本會期召委」，語意才正確。

## 三、次要問題（不阻斷，但該修）

1. **ID9 沒有 `lgno` 欄位** → `id` 退化成陣列索引 `` `LY-${i}` ``。排序一變，追蹤（⭐）就對不上人。改用姓名或 `ename` 當 key（PoC 已改）。
2. **123 筆含 10 筆 `leaveFlag=是`**（已離職／已遞補）→ 未過濾，名錄會多出非現任者；過濾後為 113 人。
3. **`log()` 在 `setState` updater 內寫 `localStorage`** —— StrictMode（`main.jsx` 有開）下 updater 可能被呼叫兩次，同步紀錄會重複。
4. **`package.json` 依賴全寫 `"latest"`** —— 無法重現建置；本次實測裝到 vite 8.3.1，未來一個 breaking change 就能讓專案開不起來。`@vitejs/plugin-react` 也該放 devDependencies。
5. **同步防重入失效**：`setInterval` 裡的 `syncNow` 閉包永遠讀到初始 `sync.state`，`if(sync.state==='loading')return` 對定時同步無效。
6. **每 6 小時抓 1.4 MB**（且 `cache:'no-store'`）：對政府端點不禮貌，也浪費使用者流量；ID14 只有 783 筆與當屆有關。
7. **無資料授權標示**：只用「立法院開放資料」字樣，未註明授權條款（政府資料開放授權條款第 1 版）與資料更新時間，正式對外發布應該補。
8. **無任何測試**：解析邏輯（`rows`/`fld`/`normalize`）全塞在 18 行超長行裡，是本專案最容易壞也最該加單元測試的部分。

| 工作 | 估時 |

| 代理層（含 SSL workaround）+ 環境變數化 API base | 0.5 天 |
| 修正 `normalize()`：同期別過濾、前綴剝除、穩定 id、leaveFlag 過濾 | 0.5 天 |
| 逐會期語意（session 選擇器、召委以本會期為準） | 0.5 天 |
| 錯誤處理/防重入/日誌修正 + 依賴鎖版 | 0.5 天 |
| 解析邏輯單元測試（用真實 API 回應當 fixture） | 0.5 天 |
| 部署（Worker/Function）與授權標示 | 0.5 天 |

**建議順序**：先做代理（否則什麼都看不到）→ 修解析 → 加測試鎖版 → 最後才談 UI 加值。

**後續加值可行性**：這兩個端點只給基本名錄與委員會，若要「法案／表決／質詢」 intelligence，需再接立法院議事及法案相關開放資料集（同樣無金鑰），單獨評估即可；目前架構（單檔元件）在功能變多前建議先拆模組。

## 六、風險清單

- **政府端點無 SLA**：可能改欄位、擋流量或再改 TLS 設定；務必在代理層加快取與逾時（現在前端 20 秒 AbortController 是好的開始）。
- **假資料上線風險**：`demo` 是預設 state，任何同步失敗都會顯示假立委；上線前應改成「無資料」空狀態。
- **CORS 不是唯一路徑**：若未來立法院提供 CORS 或靜態檔案下載端點，可直接抓檔；但**不要**依賴 JSONP 或第三方 CORS 代理（資安與穩定性都不可接受）。

## 附註：原始碼品質觀察

整包 7 檔、App.jsx 只有 18 行但每行數百字元，`normalize` 的欄位猜測（`fld(o,...k)` 多別名）與 `rows()` 的遞迴攤平是務實的防禦性寫法，看得出對 API 不確定性有準備；
但這種「一行到底」的寫法讓 B3/B4 這類解析錯誤極難被察覺，也沒有測試保護 —— 這是本專案最大的技術債，也是維運風險的來源。
